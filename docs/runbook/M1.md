# madc M1 runbook

*Operator's guide to the M1 build ("every lane lit + named roster"). About 12 minutes to read.
The mock paths need no key and no network. Every live step is optional: you run it yourself with
your own keys or vendor sign-ins, it may use plan quota or paid credit, and CI never runs it.*

Every `madc …` below means `node packages/cli/src/bin.ts …` run from the repo root after
`npm ci` (swap `node` for `bun` freely). `madc --help` lists the commands. Everything madc keeps
lives in `$MADC_HOME` (default `~/.madc`). `madc doctor --init` seeds it. The
[M0 runbook](M0.md) still covers install, doctor's rows, the session files and the Witness app.

**One M1 limit to know first.** No shipped surface claims `mode: "interactive"`. `madc -p` is
headless by definition, and the Witness app (`madc`, `madc -s <seat>`) sends no mode, which the
engine reads as headless. So `ollama-cloud`, `minimax-token-plan`, `alibaba-coding-plan` and the
`surface-architect` seat refuse every turn you can start from the CLI. The engine half (the claim
plus the engine's own keypress check on `/dev/tty`) is built and mock-tested; a client that uses it
is not part of M1.

## 2. Keychain setup

Keys live only in the OS keychain (D-M1-5). madc never takes a key from a file, a flag or the
protocol stream.

```sh
madc auth set <id>      # no-echo prompt on your terminal; the key is never an argument
madc auth status <id>   # presence only, never the value
madc auth rm <id>
madc providers ls       # PRESENT column: "creds yes/no" or "binary yes/no"
```

`auth set` takes the direct-key ids in §1 (and the unwired direct stubs, which nothing reads). It
refuses `claude-code`, `codex` and `grok-build` with exit 4: those tools sign in themselves, and
madc never stores consumer-login tokens. Every `madc` command starts a fresh engine, which reads the
keychain once, so a newly stored key applies from the next command.

### macOS

Nothing to install. madc runs `/usr/bin/security` against your login keychain: one generic password
per lane, service `madc`, account `<id>`. To check an item without printing it, run
`security find-generic-password -s madc -a <id>` and never add `-w`, which prints the secret.
Keychain Access lists the same items under "madc". Known exposure: Apple's tool takes the secret as
its own `-w` argument, so while `security` runs, another process of your user could read it from a
process listing.

### Linux

madc runs `secret-tool` (libsecret) against the Secret Service. You need:

1. `secret-tool` on PATH (Debian/Ubuntu: `sudo apt install libsecret-tools`; elsewhere, the package
   that ships `secret-tool`);
2. a running, unlocked Secret Service provider in your login session, for example GNOME Keyring, or
   KeePassXC with its Secret Service integration turned on.

Items carry the attributes `service madc provider <id>` and the label `madc <id>`; the key reaches
`secret-tool` on stdin, never as an argument. Check with `madc auth status <id>`, not
`secret-tool lookup`, which prints the key. Over SSH or on a server with no session bus there is
usually no Secret Service, and `auth set` fails with exit 1.

### The development exception

`MADC_DEV_ENV_KEYS=1` also lets the engine read `MADC_API_KEY_<ID>` from the environment
(`kimi-code` reads `KIMI_API_KEY`), and lets `auth set` read the key from stdin without a terminal.
It is for development only. Without the flag, environment keys are ignored, and doctor's
`cred.kimi-code` row says so. Windows has no keychain backend in M1.

## 3. Optional live smoke, per subscription

For each lane: store the key or sign the vendor tool in, run one trivial turn such as
`madc -p "Reply with the word ok." -s <seat>`, then read the receipt (§5). For a lane with no
seeded seat, copy `$MADC_HOME/seats/madc-default.json` to `$MADC_HOME/seats/<new id>.json` and change
`id`, `preferredBacking` and `pinnedModel`. A `pinnedModel` the lane cannot resolve is refused with
`-32006` before any call.

| Subscription | Setup | Seat | Expect |
| --- | --- | --- | --- |
| Kimi Code | `madc auth set kimi-code` | `prometheus` | served |
| Claude Pro/Max | `claude` signed in by you | `daedalus` | served |
| ChatGPT → Codex | `codex` signed in by you | `hephaestus` | served |
| Grok Build | §3.1 | `grok` | served |
| Mistral Pro | `madc auth set mistral-pro` | `pinnedModel: "mistral/<id>"`, e.g. `mistral/mistral-small-latest` | served |
| Gemini API | `madc auth set gemini-api-key` with an **auth** key | `google/<id>`, e.g. `google/gemini-2.5-flash` | served |
| xAI API | `madc auth set xai-api` with an API key | `xai/<id>`, e.g. `xai/grok-4.7` | served |
| DeepSeek | `madc auth set deepseek-payg` | `deepseek/<id>`, e.g. `deepseek/deepseek-flash`; run inside a git repo | **refused** (§3.2): `repo gate deepseek-payg: deny (repo-not-allowed)` |
| Ollama Cloud | `madc auth set ollama-cloud` | `surface-architect` | **refused**: `presence ollama-cloud: absent (the turn is headless)` |
| MiniMax Token Plan | `madc auth set minimax-token-plan` (`sk-cp-…` only) | `minimax/<id>`, e.g. `minimax/MiniMax-M3` | **refused**: `presence minimax-token-plan: absent (…)` |
| Alibaba Coding Plan | `madc auth set alibaba-coding-plan` (`sk-sp-…` only) | `alibaba-coding-plan/<a model id your plan lists>` | **refused**: `presence alibaba-coding-plan: absent (…)` |

The four refused rows are the live check M1 can offer for those lanes: with your real key present,
madc refuses before it contacts the provider. Each prints `error provider -32007: Provider denied by
registry`, `turn NOT STARTED`, `NO RECEIPT`, exit 4, and the `[madc-engine]` line quoted above on
stderr. The protocol error also carries the pinned reason (`repo-not-allowed`,
`headless-not-permitted`, `interactive-only-headless`), which the M1 CLI does not print. The example
model ids are in the pinned pi-ai 0.87.1 catalog, which is what madc checks; whether your account
may use one is the provider's answer.

Other answers you may see (each `-32007` / `-32008` exits 4):

| Answer | Meaning |
| --- | --- |
| `-32008 no-credentials` | No key stored, or a plan lane holds a key of the wrong class. |
| `-32008 binary-missing` | The vendor tool is not on PATH. |
| `-32008 quota-or-unreachable` | The provider answered 429 or 502; the seat's same-lane fallbacks were tried first. Gemini cannot report this: pi-ai 0.87.1 hides the status, so a Gemini 429 is an ordinary turn failure (exit 1). |
| `-32006` | The seat file or its `pinnedModel` is invalid for the lane. |
| a "likely to fail" line on stderr | `gemini-api-key` holds a standard `AIza…` key. The catalog's quoted source (roadmap §3 row 5) says standard keys are rejected from September 2026. |

Mock-only test runs: `npm run test:node` / `bun test` make **one real Claude Code call** when `claude`
is on PATH (`packages/adapters/src/claude-code.test.ts`), and the pre-push hook runs both. Take
the vendor binaries off PATH for a mock-only run. The Codex and Grok live tests also need an
opt-in model variable (`MADC_TEST_CODEX_LIVE_MODEL`, `MADC_TEST_GROK_LIVE_MODEL`).

### 3.1 Grok Build

Requires the **unmodified** `grok` binary on PATH (checked against grok 1.0.44), signed in by Grok
Build itself: either `grok login` (your SuperGrok / X Premium+ login, held by Grok Build only) or
`XAI_API_KEY` exported in the shell that runs madc (the API-key class). madc never reads `~/.grok`
or any Grok credential file, never reads the key's value (it only checks whether `XAI_API_KEY` is
set, to pick the matching ACP auth method), never hands Grok the `xai-api` keychain key, and never
uses pi-ai's xAI OAuth.

**Seat it:** copy `$MADC_HOME/seats/madc-default.json` to `$MADC_HOME/seats/grok.json` and change
three fields: `id: "grok"`, `preferredBacking: "grok-build"`, and `pinnedModel` set to a model id
that `grok models` lists for your sign-in. Then `madc -p "Reply with the word ok." -s grok`.

One child per turn: `grok --no-auto-update agent --no-leader --model=<pinnedModel> stdio`, driven
over ACP (`initialize` → `authenticate` with `_meta.headless` → `session/new` → `session/prompt`).
`vendorReported` is `true` only if Grok reported its model through ACP. A protocol `turn/interrupt`
sends ACP `session/cancel` to Grok, then stops the child. Grok Build is the one vendor lane whose
tool use shows up as `toolCall` / `toolResult` items.

**Adapter-only live check** (no engine, fixed trivial prompt, answer never printed):

```sh
MADC_TEST_GROK_LIVE_MODEL=<model id from `grok models`> \
  node --test packages/adapters/src/vendor/grok-build.test.ts
```

| Result | Meaning |
| --- | --- |
| `-32008 binary-missing` at `turn/start` | `grok` is not on PATH. |
| turn `failed`, `-32008 no-credentials` | Grok Build offered no usable sign-in or refused it. Run `grok login`, or export `XAI_API_KEY`. |
| `-32006` at `turn/start` | `pinnedModel` is empty or not a plain model id (for example it starts with `-`). |

**Approval posture:** madc never passes `--always-approve`. If Grok asks for permission over ACP,
madc refuses (M1 has no approval surface). madc cannot see or limit tool use that Grok runs
without asking; Grok's own permission settings govern that.

### 3.2 DeepSeek and MiniMax repo allowlists

Both lanes are repo-gated by `$MADC_HOME/policy.json`. With no file, or an empty list, every
repository is denied. Naming a repository is a Founder decision (D-M1-8 for DeepSeek; D-M1-9 for
MiniMax, non-sensitive repos only), and it is not an M1 exit requirement. If you decide to name one,
write the file yourself (madc never writes it) and `chmod 600` it:

```json
{ "version": 1, "repoAllow": { "deepseek-payg": ["github.com/<owner>/<repo>"] } }
```

The engine resolves the repository from the thread's working directory itself: the realpath of the
git top-level plus the normalized `origin` URL, matched exactly (no prefixes, globs or case
folding). Doctor's `policy` row reports what loaded and any entry it rejected. Every decision is
written to the session as a `repo.decision` event.

## 5. How to read a receipt

A one-shot ends with this block on stderr (the mock path of M0 runbook §3; ids and path
shortened):

```
─ receipt ─────────────────────────────────────────────
 turn     COMPLETED            turn_9424d539b3c1…       0.1s
 model    kimi-coding/kimi-for-coding → kimi-for-coding   (kimi-code)
 session  ~/.madc/sessions/thr_5c783fc7b3ba….jsonl
          seq 6 · head 145f7fe47fa0 · chain VERIFIED
 exit     0
```

`model` reads *requested → served (backing)*. `session` gives the file, its last `seq`, the first
12 hex digits of the head hash and the chain verdict: `chain VERIFIED` means madc re-read the file
after the turn and every hash matched. With `--json`, the same four fields arrive in one
`servedModel` object on stdout.

The full receipt is the session file's `servedModel` event:

```sh
grep '"type":"servedModel"' "$MADC_HOME/sessions/<threadId>.jsonl"
```

| Field | Meaning |
| --- | --- |
| `requestedModel` | The seat's `pinnedModel`. |
| `servedModel` | The model the provider or vendor reported, else the requested id. |
| `vendorReported` | `true` only when madc knows the vendor reported its own model id, which is then `servedModel`. `false` means "not known", and `servedModel` repeats the request. Mistral, Gemini and xAI are always `false` (pi-ai 0.87.1 does not surface their model field). Most other lanes read `true` only when the reported id differs from the requested one, because madc cannot tell an echo from a report; Grok Build says so either way. It can under-claim, never over-claim. |
| `providerId`, `backing` | The registry id that served this call; in M1 both name the serving lane. |
| `lane` | That id's registry status, e.g. `allowed-direct`. |
| `mode` | The turn's mode: always `headless` from today's CLI (§1). |
| `fallbackFrom` | `null` on the seat's own backing; on a fallback hop, the lane that failed before it. |

Nearby events in the same file: `turn.start` (`mode`, `presence`), `item` (the user and agent
messages, and `toolCall` / `toolResult` for Grok Build), `fallback.rejected` (a listed fallback
refused because its status or billing differs from the seat's lane, D-M1-7), `repo.decision` (§3.2)
and `turn.end`. Doctor's `session` row re-verifies the latest session; its head hash matches the
receipt's, and editing any line breaks both.

## 6. Known limits in M1

- The presence keypress stops detached automation, not a hostile program running inside your own
  terminal (M1-A5).
- madc cannot see or limit the tool use a vendor agent runs without asking; Claude Code, Codex and
  Grok Build follow their own permission settings. Only Grok Build's tool use is surfaced as items.
- Seat `tools.deny` lists are recorded and reach the model through the seat's standing
  instructions, but nothing enforces them in M1.
- No client surface claims an interactive turn (§1).
