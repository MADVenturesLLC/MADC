## Recommendation

**(c) Hybrid: pin `@earendil-works/pi-ai` behind MAD provider interfaces; MAD owns the agent loop, seats, policy, session hash-chain, MCP, and subagents.**

pi-ai already solves the hardest commodity problem (many providers, OpenAI/Anthropic wire adapters, headers, streaming, usage/cost, `responseModel`). pi-agent-core's loop is competent and has `beforeToolCall`, but MAD still must build named seats, rules-aware registry policy, hash-chained session records, MCP, subagents, and Claude Code / Codex app-server adapters on top. Owning the loop avoids being dragged by weekly 0.x breaks in agent-core while still reusing pi-ai. If MAD later wants the stock loop, it can adopt `pi-agent-core` behind the same seat interface without rewriting providers.

What MAD would still build in each option:

- **(a) Full Pi libs pinned:** MAD still builds seats, hash-chained persistence, MCP, subagents, Claude Code/Codex adapters, sandbox/OS policy beyond `beforeToolCall`, and a rules-aware registry wrapping pi's providers. Accept frequent pin bumps.
- **(b) Clean MAD core only:** MAD rebuilds provider adapters (months of work pi-ai already did), plus everything in (a).
- **(c) Hybrid (recommended):** MAD builds loop+seats+policy+MCP+subagents+adapters; reuses pi-ai for provider I/O behind MAD interfaces; optionally borrows patterns from `beforeToolCall` / event shapes without taking agent-core as a hard dependency on day one.

### Custom base URLs and headers (including honest User-Agent for Kimi)

pi-ai supports:

- Per-model `baseUrl` and `headers` on the model object
- Per-request `options.headers`
- Collection-level `transformHeaders` after auth/model/explicit merge (`packages/ai` README; `dist/models.js` around the `transformHeaders` call)

Default User-Agent is `getPiUserAgent()` → `pi (<os>...)` (`dist/utils/pi-user-agent.js`). For Anthropic-compatible paths (including `kimi-coding`), headers are merged with `mergeClientHeaders` so later sources can override User-Agent (`dist/api/anthropic-messages.js`).

**Runnable proof** (mock OpenAI server; Node and Bun): requesting with

`headers: { "User-Agent": "MAD-Agent/1.0 (honest-identity)", "X-Extra": "yes" }`

and `model.headers: { "X-Client-Identity": "mad-pi-check" }` produced on the wire:

```
CAPTURED_USER_AGENT MAD-Agent/1.0 (honest-identity)
CAPTURED_X_CLIENT mad-pi-check
CAPTURED_X_EXTRA yes
PASS custom-headers
```

So client identity for Kimi Code can be set per provider/model/request without forking pi-ai.

- Ollama is documented custom provider, not a first-class catalog with auto model discovery unless MAD implements `fetchModels`.
- Exact DashScope “coding plan” SKU naming vs `qwen-token-plan*` catalog entries was matched by endpoint/provider naming in the shipped JSON catalog; live Alibaba account behavior was **UNVERIFIED** (no API key by design).
- Live Kimi Code User-Agent acceptance was **UNVERIFIED** against the real endpoint; only header plumbing was proven.

## 2. Permission gate on every tool call — PARTIAL

### What the source says

`AgentLoopConfig` in `@earendil-works/pi-agent-core` (`dist/types.d.ts`):

- `beforeToolCall?: (context, signal?) => Promise<BeforeToolCallResult | undefined>`
- `BeforeToolCallResult`: `{ block?: boolean; reason?: string; terminate?: boolean }`
- Docs: called after args are validated, **before** execution; `{ block: true }` prevents execution and emits an error tool result.

Implementation (`dist/agent-loop.js`, `prepareToolCall`): if `beforeResult?.block`, returns an immediate error result and never reaches `tool.execute`.

Upstream README (`earendil-works/pi`): “Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access.” That refers to **OS/sandbox permissions**, not the absence of a tool hook. The older recollection “ships without permissions, MCP, or subagents by design” is:

- **Permissions (sandbox):** still true for coding-agent defaults
- **Tool deny hook:** **false** for current agent-core — `beforeToolCall` exists
- **MCP / subagents in agent-core:** still true — not part of the core loop package (coding-agent/extensions/community adapters exist; mcp-adapter is separate)

`beforeToolCall` cannot rewrite tool arguments. Result shaping is `afterToolCall` (post-execution). Per-tool `prepareArguments` can reshape args but is not a central policy gate.

### Runnable proof

`/workspace/pi-check/test-permission-gate.mjs` using `fauxProvider` + `Agent` with `beforeToolCall` returning `{ block: true, reason: "policy-denied:dangerous_shell" }`:

```
BEFORE_SAW {"name":"dangerous_shell","args":{"cmd":"rm -rf /"}}
EXECUTE_COUNT 0
BLOCKED_RESULT policy-denied:dangerous_shell
PASS beforeToolCall-deny
```

Same PASS on Node `v22.19.0` and Bun `1.4.2`.

### Why PARTIAL not PASS

Deny-before-execute is proven. “Modify” of the pending tool call (args/name) via the permission hook is not supported. MAD still must implement richer policy (path allowlists, network, MCP tool mediation, seat-level rules).

## 3. Served model id reaches the engine — PASS

`AssistantMessage` (`pi-ai` `dist/types.d.ts`):

```ts
model: string;
responseModel?: string;
```

OpenAI Completions adapter (`dist/api/openai-completions.js`):

```js
if (typeof chunk.model === "string" && chunk.model.length > 0 && chunk.model !== model.id) {
  output.responseModel ||= chunk.model;
}
```

Anthropic Messages adapter similarly sets `output.responseModel` when `event.message.model !== model.id`.

### Runnable proof

Mock server always returns `"model": "served-openai-model-abc"` while the client requested `requested-model-id`:

```
REQUESTED_MODEL_FIELD requested-model-id
RESPONSE_MODEL_FIELD served-openai-model-abc
PASS responseModel
```

Node and Bun both PASS. Session records can log `response.model` (requested catalog id) and `response.responseModel` (server-reported id when different).

## Additional notes (brief)

| Topic | Finding |
|-------|---------|
| Streaming / abort | First-class: `stream` / `streamSimple`, `AbortSignal` → `stopReason: "aborted"`, partial content retained |
| Tool-call normalization | Unified `toolCall` content blocks + TypeBox validation (`validateToolCall`); provider differences handled in API adapters |
| Token / cost accounting | `Usage` with `input`/`output`/`cacheRead`/`cacheWrite`/`totalTokens` and nested `cost` dollars from model metadata |
| Session persistence | `pi-ai` Context is JSON-serializable (caller persists). `pi-agent-core` does not own durable sessions by default; optional SQLite backend is a **separate** package `@earendil-works/pi-session-backend-sqlite-node`. Hash-chained session records are **MAD's job** |
| Local server + thin clients | Libraries are in-process. No conflict if MAD wraps them in a local RPC/HTTP server; do not treat coding-agent TUI as the server. Avoid assuming Pi manages multi-client seats |
| MCP / subagents | Not in `pi-agent-core`. Appear in coding-agent / extensions / forks (e.g. omp). MAD should not count on upstream core for these |

## oh-my-pi (omp) as an alternative

- Relationship: documented fork of Pi (`can1357/oh-my-pi`), coding-first rewrite with sessions, subagents, slash commands, extensions, MCP discovery.
- SDK: `@oh-my-pi/pi-coding-agent` — embeddable session API (`createAgentSession`, `SessionManager`, hooks). npm `18.3.0` with **`engines.bun: ">=1.3.14"`**; docs: Bun SDK, not Node.
- Viability for MAD: useful reference for seats/subagents/MCP UX, but **not** a drop-in for a Bun+Node 22 local engine unless MAD accepts Bun-only or keeps omp out-of-process via its RPC mode. Prefer upstream `pi-ai` for provider coverage under Node.

## Surprises

1. Package rename/move: production deps should be `@earendil-works/pi-*`, not `@mariozechner/pi-*` (deprecated at `0.73.1`).
2. `beforeToolCall` already exists — the “no permissions” README line is about sandboxing, not missing a deny hook.
3. `responseModel` already solves served-vs-requested model logging for OpenAI- and Anthropic-compatible paths.
4. Engine floor is Node **22.19+**, not “any Node 22”.
5. Release velocity is extreme for a library pin (~weekly minors); hybrid reuse of `pi-ai` only is the lower-risk way to buy provider coverage.
