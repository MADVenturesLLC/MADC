## 1. Launcher: `madc-engine serve`

1. **Subcommand.** `madc-engine serve` is intercepted in `packages/engine/src/bin.ts` **before** the stdio engine starts, exactly as `auth-set` is today (`bin.ts:11-16` @ `bd037b4`: `argv[0] === "auth-set"` runs `runAuthSet` and sets `process.exitCode`; every other invocation calls `startStdioEngine()`). `serve` takes no further arguments.
2. **Socket only.** `serve` starts **only** the local-socket listener (`startSocketServer`, `socket.ts:48` @ `6e20176`). It runs **no** JSONL session on its own stdin/stdout: it never parses protocol from stdin and never writes to stdout. stderr carries logs only (M1 pin §1, line 33).
3. **Its stdio.** `serve` **reads and discards** everything on stdin and only watches for EOF (§3 a). The launcher spawns it with stdin a pipe the launcher holds open, stdout `"ignore"`, and stderr a pipe the launcher **drains for the whole life of `serve`, until it exits** (so `serve` never blocks on a full stderr pipe), keeping it for §5.
4. **Who launches it in M3.** The desktop app (`packages/desktop`, M3-A2 onward) is the **only** launcher.
5. **The CLI is unchanged.** It still spawns a stdio child per M1 pin §2 (line 45, `stdio: ["pipe","pipe","inherit"]`, and line 46) and does not use the socket in M3.
6. **No daemon.** No launchd or systemd unit, no login auto-start, no detach or double-fork, no `setsid`, and no TCP, WebSocket or HTTP listener. The base pin's "does not add remote/TCP access" (line 7) and M1 pin §6 "daemon; remote attach" (line 300) stand.
7. **No new method.** Nothing on the socket can stop `serve`; there is no shutdown request. A client only ends its own connection.

## 2. One listener per `$MADC_HOME`

**Enforced** by `engine.lock` (§2a), inside the M0 Amendment 2 §1 envelope (one PID namespace, one host, one kernel boot; lines 19-27).

Before spawning, the launcher probes `engine.sock` (path from `engineSocketPath(home)`, `socket.ts:22-28` @ `6e20176`, with the §4 Windows hash change):

- If a listener accepts the connection **and** answers `initialize` with `protocolVersion: "madc-m1/1"` within **1 s** (connect plus reply), the launcher uses that connection and does not spawn.
- Otherwise it spawns `serve`, which takes `engine.lock` and runs its §4 checks, refusing with exit 20 or 21 if the home is owned or the path unsafe.
- **On child exit 20** (a live `engine.lock` holder, a live listener, or `EADDRINUSE`), the launcher **re-runs the §2 probe once**, retrying `connect()` until the 5 s start window (§5) ends, because a holder that is still starting may not be listening yet. If a listener answers, it connects to it. That is not a respawn. If the re-probe fails, it reports the failure (§5), including the §2a recovery text when the reason line names a lock holder.
- **Windows path.** The launcher computes the pipe name from `fs.realpathSync.native(MADC_HOME)` (canonical case). If `$MADC_HOME` does not exist yet, there is no listener: it spawns `serve`, which creates the home.

A launcher that reuses another launcher's listener does not own it: that `serve` ends when **its** launcher ends (§3).

## 2a. `$MADC_HOME/engine.lock` (lifetime lock)

`serve` takes an exclusive lifetime lock at `$MADC_HOME/engine.lock` **after** the home checks and **before** §4 step 1, and holds it until **after** the final `engine.sock` unlink (§3 step 5). It uses the M0 Amendment 1 scheme and `lock.ts`'s rules **unchanged**; only the path differs:

- **Body and token:** exactly `{ pid, startedAt, token }`, `token` 128 random bits as 32 lowercase hex, fresh on every acquisition, kept in memory, never logged, never on the wire (M1 pin lines 98 and 103 (d); `lock.ts:16-23`, `:54-56`).
- **Create:** exclusive create through a private temp file hard-linked into place (`createExclusive`, `lock.ts:181-195`), up to five attempts (`lock.ts:259`).
- **Live holder:** a holder whose pid is alive, whatever its token, means the home is owned (M1 pin line 102 (c); `lock.ts:263-269`, `isPidAlive` `:166-174`). **`serve` exits 20.** So does running out of attempts (`lock.ts:275`).
- **Stale holder and reclaim:** a dead pid or a corrupt body is reclaimed by rename-aside, re-read, and delete only if byte-for-byte unchanged, else restored (M1 pin line 101 (b); `reclaimIfUnchanged`, `lock.ts:219-245`). A symlink at the path is treated as corrupt, never followed, and reclaimed like any corrupt body (`lock.ts:156`); a non-regular file other than a symlink (directory, FIFO, device) is refused (`LockPathNotAFileError`, `lock.ts:153-163`): **exit 21**, as is any other I/O error taking the lock.
- **Release:** only if the on-disk token is this holder's, and only if the path still names the file whose body was checked (M1 pin line 100 (a); `releaseThreadLock`, `lock.ts:323-338`).
- **Envelope and residuals unchanged:** cross-namespace reclaim and the three-engine reclaim race (M0 Amendment 2 §1, §6 lines 78-91) apply to `engine.lock` as they do to thread locks.
- **No per-append re-check, so `serve` re-verifies.** A thread lock's three-engine race is bounded by the per-append ownership re-check (M0 Amendment 2 §2, lines 29-42; §6 lines 83-90: R1's next append fails `-32009`). `engine.lock` guards no appends, so it has no such re-check, and in that race two `serve`s could both believe they own the home. `serve` therefore re-verifies that the lock still carries its token (`holdsThreadLock`, `lock.ts:340-347`, which also checks the path still names the file read) **twice**: just before §4's unlink, and just after `listen` succeeds. If the token is gone at either point, `serve` closes its server (if listening), unlinks only its own socket (same `dev`+`ino`, §3 step 5 rule), and **exits 20**.
- **Crash residue can keep the lock looking held (carried risk).** After SIGKILL, an OOM kill or power loss, `engine.lock` keeps the dead `serve`'s pid. `isPidAlive` treats any `kill(pid, 0)` result other than `ESRCH` as alive (`lock.ts:165-174`), so if that pid has been reused by a live process, or belongs to a process this user may not signal (`EPERM`), the lock looks held: Argus's probe shows `kill(1, 0)` returning `EPERM` as uid 1000 (`logs/amend1/pidreuse.log`). Every `serve` then exits 20 until that pid ends, and after a reboot this is the normal case. The rules stay unchanged; the way out is pinned instead:
  1. `serve`'s exit-20 reason line names the lock path **and** the holder pid (`madc-engine serve: home owned by pid <pid>: <path to engine.lock>`); the pid is public, the token is never printed. The line is written with a write callback and `serve` exits only from that callback or after its 2 s grace (§3, "Explicit exit on every path"), so it reaches the launcher even when stderr is backed up.
  2. The launcher, which drains `serve`'s stderr (§1.3), shows both to the user with this manual fix: **(i)** confirm no `madc-engine serve` process with that pid is running (for example `ps -p <pid> -o command=` on POSIX, or Task Manager on Windows); **(ii)** if none is, remove `$MADC_HOME/engine.lock`. The launcher never removes the lock itself.
  3. **Not adopted:** treating a holder whose `startedAt` is before the current boot (`Date.now() - os.uptime() * 1000`) as dead. That is a lock-rule change and is left for a Founder ruling.

**Required in `lock.ts`.** `acquireThreadLock` builds its path from a thread id (`threadLockPath`, `lock.ts:50-52`, `:257`) and cannot take `$MADC_HOME/engine.lock`; `releaseThreadLock` and `holdsThreadLock` take a handle and work on any path (`lock.ts:323-347`). So:

- `lock.ts` gains one exported acquire that takes a path, `acquireLockAt(home, path, pid = process.pid)` (the same parameter shape as `acquireThreadLock(home, threadId, pid = process.pid)`, `lock.ts:252-256`), which refuses any `path` not strictly inside `$MADC_HOME` (`isStrictlyUnder`, `home.ts:36-39`) and runs exactly the steps of `acquireThreadLock` (`lock.ts:252-276`).
- `acquireThreadLock` delegates to it **unchanged** in behavior: `acquireLockAt(home, threadLockPath(home, threadId), pid)`.
- The existing lock tests (create, live holder, reclaim, the three-engine race, symlink, non-regular file, release and hold checks) also run against `engine.lock`, and the PR lists the mutation id each one kills.
- **New test, "engine.lock token lost → exit 20, no socket left":** with the token removed from `engine.lock` (a) just before §4's stale unlink and (b) just after `listen`, `serve` exits 20 and no `engine.sock` it bound remains; the PR lists the mutation id it kills (for example, skipping either re-verify).

**Why the lock.** Without it, two `serve`s on one stale socket can both pass the §4 checks, and the second unlinks the first's new socket by path (Argus pre-check M2). With `engine.lock` held, no other `serve` on the same home can be between §4's check and its unlink at the same time, which is what closes the check-then-unlink gap (COPILOT-PATTERNS #4) for `serve` against `serve`. A non-`serve` actor that swaps the path inside that window is not excluded: POSIX has no compare-and-unlink, so that residual stays, narrowed by the `dev`+`ino` re-check.

## 3. Lifetime

`serve` runs until the **first** of:

- **(a) EOF on its stdin.** Because the launcher holds the stdin pipe open, the engine ends when its launcher exits or crashes and does not orphan. A `serve` started with stdin already at EOF (for example `</dev/null`) shuts down at once.
- **(b) SIGTERM or SIGINT.**
- **(c) A fatal listener error** after listening started (the server emits `error`): exit 22.
- **(d) An unexpected internal fault:** `serve` installs `uncaughtException` and `unhandledRejection` handlers that write one reason line, attempt this shutdown, and exit 24. Once its handlers are installed, `serve` never exits with the runtime's default 1; a fault while the module is still loading, before they are installed, exits 1 and the launcher reads it as 24 (§6).

**Explicit exit on every path.** Every `serve` exit path releases its locks, writes the final reason line (non-zero exits) **with a write callback**, and then calls an explicit `process.exit(code)` **from that callback, or when its grace runs out if the callback never comes**, whichever is first. The grace is **`min(2 s, 6 s − the time since the first lifetime-ending trigger)`** (§3 a-d); a startup refusal, which has no lifetime trigger, uses the plain 2 s. So once a lifetime trigger has fired, `serve` is always gone **by 6 s** after it, 1 s inside the launcher's unchanged 7 s SIGKILL (§5). The pattern is the stdio engine's signal path (`handleTerminationSignal`: a 2 s `setTimeout` grace, `main.ts:301`; exit from the write callback, `main.ts:304`; `exitOnce` → `deps.exit()`, `main.ts:298`, which is `process.exit()`, `main.ts:278`). Because the launcher drains stderr for the whole life of `serve` (§1.3), the callback normally comes at once. An exit 23 (§3 Deadline) and its reason line therefore beat the 7 s SIGKILL unless stderr stays blocked for the whole window; if it does, the reason line may be lost, but `serve` still exits 23 by 6 s. An error passed to the write callback (for example `EPIPE` when the stderr reader has gone) is ignored and `serve` still exits with its code (Argus probe `logs/amend1/epipe.log`: with an `uncaughtException` handler installed, a closed reader gives the callback `EPIPE` and a closed fd 2 gives it no error, and both exit with the intended code 20 on Node v24.22.1, Bun 1.4.4 and Bun 1.3.11; no exit 24, no hang). A child that never initialized can be SIGKILLed 2 s after SIGTERM (§5), so its line arrives only if the write completed by then. Calling `process.exit()` straight after the write is not allowed: POSIX pipes are asynchronous, and with more than one pipe buffer (64 KiB on Linux) of stderr unread, the line is lost (Argus probe `logs/amend1/exitflush.log`, `shellpipe` lines: with 200000 log bytes, exit-now delivers 65536 bytes and no final line on Node v24.22.1, Bun 1.4.4 and Bun 1.3.11; flush-then-exit delivers all 200057 bytes and the line on all three; at 60000 bytes or fewer both deliver it). **Required test:** a slow stderr reader that leaves more than 64 KiB unread before it starts draining still receives the final reason line. `serve` never relies on the event loop draining or on a top-level `await` settling. Measured (`logs/amend1/rt/probes.log`): with a top-level `await` that never settles, Node v24.22.1 exits 13 only when `process.exitCode` is unset (with it set to 21 it exits 21), and Bun 1.3.11 and 1.4.4 never exit; they hang until killed (here by `timeout` after 5 s). With the handlers installed, an uncaught exception, an unhandled rejection and a rejected top-level `await` all exit with the handler's code on Node v24.22.1, Bun 1.3.11 and Bun 1.4.4; without handlers all three exit 1.

**Shutdown sequence** (the same for every trigger):

1. Call `server.close()` (stop accepting connections); its callback is awaited at step 4.
2. Each connection runs `EngineConnection.shutdown()` **unchanged** (`server.ts:512-533` @ `bd037b4`), keeping every step it has: the once-only guard (`:513-514`); abort of pending presence prompts (`:516-517`); in-flight turns end `interrupted` (`:518-522`, as M1 pin §2 lifecycle step 5, line 55); `session.close` written for each loaded thread under the lock this process still holds, **before** the thread locks are released, with release in a `finally` (`:523-530`; D-M2-A0-5, `PIN-madc-M2-evidence-schema-v2.md` line 161 and row line 379); marking the connection closed (`:531`); and closing its readline (`:532`).
3. Each client socket is **ended** (`end()`), then **destroyed** (`destroy()`) on that socket's `finish` event or when a **per-socket 2 s grace** runs out, whichever comes first, all inside the 5 s deadline. This matches the stdio engine's 2 s flush bound (`main.ts:301` @ `bd037b4`, flush detected by write callback at `:304`). `destroy()` straight after `end()` is not allowed: it discards unflushed writes (Argus pre-check M1, `logs/amend1/run.log`: 219264 of 4194332 bytes received; COPILOT-PATTERNS #10). **Test note for builders:** teardown tests must use a client that keeps reading (a flowing reader) or runs in a separate process. On Bun 1.3.11 (CI) an in-process client that is paused and resumed after the peer ends receives 0 bytes even with `end()` alone (`logs/amend1/b11v.log`), while a separate-process client receives everything (`logs/amend1/xs.log`).
4. Await the `server.close()` callback from step 1. It cannot hang, because step 3 destroys every socket within its grace (the hang fixed in `6e20176`; `socket.ts:117-124` @ `6e20176`).
5. `engine.sock` is unlinked **only if** `lstat` still shows a socket with the same `dev`+`ino` this process bound. Because `engine.lock` is still held, no successor `serve` (inside the envelope) can have bound there.
6. Release `engine.lock` (§2a).

**Locks on every exit path.** As the stdio engine does (`process.once("exit", () => conn.releaseLocks())`, `main.ts:253` @ `bd037b4`), `serve` registers a process-exit handler that releases every thread lock still held and `engine.lock`. It runs on every exit, including 23 and 24. Only SIGKILL skips it; the next start then reclaims the dead holder's locks under §2a.

**A failing shutdown step** writes one stderr log line and the sequence continues with the next step. The exit keeps the trigger's code, or 23 if the deadline passes (§6).

**Deadline.** Shutdown has a **5 s** deadline from the first trigger. When it expires, `serve` writes its final reason line and exits anyway with 23 (§6), from the write callback or at the latest **6 s** after the first trigger (§3, "Explicit exit on every path"). A second trigger during shutdown changes nothing.

A connected client that is not the launcher does **not** keep `serve` alive, and its disconnect does not stop it.

## 4. Stale-socket rule (POSIX; narrows base §1 line 16)

With `engine.lock` held (§2a), in this order:

1. **`lstat($MADC_HOME/engine.sock)`.**
2. **`ENOENT`:** go to `listen`. **Any other `lstat` error** (`EACCES`, `ENOTDIR`, `ELOOP`, `EIO`, …): **refuse.** Exit 21.
3. **Present and not a socket** (a symlink, regular file, directory, FIFO, device, or anything for which `isSocket()` is false): **refuse, do not unlink.** Exit 21.
4. **A socket:** probe `connect()` with a **1 s** timeout.
   - The probe connects (a listener answers): **refuse, do not unlink.** Exit 20.
   - The probe times out: **refuse, do not unlink.** Exit 21.
   - The probe fails with `ECONNREFUSED`, **or** with `ENOENT` on the path step 1 verified as a socket: **stale.** Re-verify `engine.lock` (§2a; token gone → exit 20). Re-`lstat`; if it is still a socket with the same `dev`+`ino`, unlink it and go to `listen`; if it is gone (`ENOENT`), go to `listen`; if it changed or the re-`lstat` fails otherwise, refuse without unlinking (exit 21). If the `unlink` itself fails with `ENOENT`, go to `listen`; **with any other error (`EACCES`, `EBUSY`, `EPERM`, …), refuse: exit 21.** The `ENOENT` case exists because Bun 1.3.11 reports a stale Unix socket as `ENOENT`, not `ECONNREFUSED` (Argus review of #73 at `6e20176`, line 129: "Bun 1.3.11 gave `ENOENT`; Bun 1.4.2 and Node gave `ECONNREFUSED`"). CI runs Bun 1.3.11.
   - Any other probe error: refuse, do not unlink. Exit 21.

**Listen (between steps 4 and 5), under umask `0o177`.** **First, the path-length check:** on POSIX, before `listen()`, `serve` refuses if `Buffer.byteLength(socketPath)` leaves no room for the terminating NUL in `sun_path` — 104 bytes on macOS and the BSDs, 108 on Linux (other POSIX platforms: 104, the smaller) — i.e. a byte length of 104 / 108 or more: **exit 22, reason `socket path too long`**. Measured on Linux (kernel 6.12, Argus probe `logs/amend1/longpath-boundary.log`, exact byte lengths): at 103, 104 and 107 bytes Node v24.22.1 and Bun 1.4.4 / 1.3.11 listen and Node and Python clients connect; at 108 Node listens (Linux accepts a full 108-byte `sun_path` with no NUL) but a Python client refuses (`AF_UNIX path too long`); from 109 Node's `listen` fails with `EINVAL`; Bun listens at every length tried. So the refusal at 108 or more is kept: one byte stricter than Node on Linux, and needed for clients that require the NUL. The macOS/BSD limit of 104 is **cited, not run**. The check does not depend on the runtime: Node v24.22.1 rejects a 133-byte path with `EINVAL`, but Bun 1.3.11 and 1.4.4 **listen** on it, and then a Node client (`EINVAL`) and a Python client (`AF_UNIX path too long`) cannot connect; only a Bun client can (Argus probe `logs/amend1/longpath.log`). Then, on POSIX, `serve` sets `process.umask(0o177)` immediately before `listen()` and restores the previous umask straight after the bind, in `listen`'s callback or its `error` handler, before anything else is created. A `listen` that fails with `EADDRINUSE` is exit 20; any other `listen` failure is exit 22. Straight after a successful `listen`, re-verify `engine.lock` (§2a; token gone → close, unlink own socket, exit 20).

5. **After `listen`:** `chmod` the socket to `0600`, then `lstat` it: it must be a socket, mode `0600`, owned by the process uid. If the `chmod` or that check fails: **close the server, unlink the socket this process bound, and refuse.** Exit 21 (fail closed; Argus L5). The umask keeps the socket from ever existing at a wider mode; the `chmod` plus `lstat` check stays as the verification.

**Windows (named pipe).** Steps 1-5's `lstat`, unlink and `chmod`, and the listen rule's umask, do not apply. The pipe name is `\\.\pipe\madc-<sha256(realpath(MADC_HOME)).slice(0,16)>`, hashing the **real path** so two spellings of one home name one pipe (`socket.ts:23-26` @ `6e20176` hashes the raw string; Argus I1, review line 192). `engine.lock` (§2a) applies. `EADDRINUSE` on the pipe is exit 20. Windows termination is a hard kill: no shutdown sequence runs and 143 is not observable; the child reports exit **1**, because both Rust's standard library and libuv call `TerminateProcess(handle, 1)` (cited from Argus's pre-check report: Rust `library/std/src/sys/process/windows.rs:726`, libuv `src/win/process.c:1385`; not run on Windows). The launcher reads that 1 as **stopped**, not 24 (§6). So on Windows the launcher always closes `serve`'s stdin first (EOF, exit 0) before any kill (§5). The owner-only pipe ACL is not pinned (§9). Nothing on Windows runs in CI: the Windows branch is **unverified**.

## 5. Launcher waits

- **Start.** After spawning, the launcher waits up to **5 s** for `initialize` to succeed over the socket (it may retry `connect()` until then).
- **Child exited 20 before `initialize`:** re-probe once per §2, retrying `connect()` until this 5 s start window ends, and connect if a listener answers; otherwise report the failure as below. When the reason line names a lock holder pid, the report includes the pid, the lock path and the §2a manual fix.
- **Deadline passed, child still running and never completed `initialize`:** SIGTERM, then SIGKILL **2 s** later if still running.
- **Stopping a child that did complete `initialize`:** close its stdin (EOF). If the launcher must signal it, SIGTERM, then wait **7 s** (the 5 s shutdown deadline plus a 2 s margin) before SIGKILL. `serve` exits by 6 s after its first trigger (§3), so the SIGKILL fires only if it hangs past that bound. On Windows, the stdin close always comes first, before any kill (§4).
- **Any failure:** show it with the child's stderr (drained per §1.3) and its exit code when it exited. **No automatic retry or respawn.**

## 6. Exit codes for `madc-engine serve`

**Existing codes, reused.** The engine process already uses `2` for a bad `$MADC_HOME` (`main.ts:222-227` @ `bd037b4`, and the CLI pin's "non-absolute `MADC_HOME` (also engine exit 2)", `PIN-madc-M0-cli.md:194`) and for `auth-set` usage errors (`auth-set.ts:112-117`, `:120`); `130` for SIGINT and `143` for SIGTERM (`main.ts:254-259`, pairs at `:255` and `:256`; `auth-set.ts:154` uses 130 for an interrupt); `1` and `4` for `auth-set` store and lane failures (`auth-set.ts:175-178`; `:134`, `:137-141`). The CLI's own table is 0-5 plus 130/143 (`PIN-madc-M0-cli.md:188-198`; `packages/cli/src/exit-codes.ts:6-15`). The new codes 20-24 appear nowhere in the engine or CLI source at `bd037b4`, and `serve` does not use 1, 3, 4 or 5, so a `serve` exit is never mistaken for an `auth-set` or CLI class. **Runtime-reserved codes.** Node.js reserves `1`, `3`-`7`, `9`, `10`, `12`, `13`, `14`, `124` and `>128` for its own runtime failures ([Node.js `doc/api/process.md`, "Exit codes"](https://github.com/nodejs/node/blob/main/doc/api/process.md#exit-codes), read 2026-11-24). `serve`'s new codes therefore sit at 20-24, outside that list; `130` and `143` are Node's own signal exits (128 + signal number) and match. A `serve` exit with any code not in the table below (including a runtime-reserved one, for example `1` from a fault before the handlers are installed) is not one of `serve`'s pinned meanings: the launcher treats it as `24`, an unexpected fault, **except** the two "stopped" rows below. An unsettled top-level `await` cannot produce one of these codes on a conforming `serve`, which always calls `process.exit(code)` (§3); without that call, Node exits 13 only when `process.exitCode` is unset and Bun hangs until the launcher kills it (`logs/amend1/rt/probes.log`).

| Code | Meaning | When |
| --- | --- | --- |
| 0 | Clean shutdown, stdin EOF | §3 (a), finished within 5 s |
| 130 | Clean shutdown, SIGINT | §3 (b), finished within 5 s (reuses `main.ts:255`) |
| 143 | Clean shutdown, SIGTERM | §3 (b), finished within 5 s (reuses `main.ts:256`); POSIX only (§4 Windows) |
| 2 | Usage or home | Any argument after `serve`; `MADC_HOME` set but not absolute; `$MADC_HOME` cannot be created `0700` or made private (`socket.ts:49-50` @ `6e20176`) |
| 20 | The home is already owned | Live `engine.lock` holder (reason line names the holder pid and lock path, §2a) or acquire attempts exhausted (§2a); lock token lost at a re-verify (§2a); §4 step 4 probe connected; `listen` `EADDRINUSE` (POSIX socket or Windows pipe). The `EADDRINUSE` mapping is a **backstop that may never fire** on Bun 1.3.11, where a second `listen()` on a live socket path succeeds and takes the path over (§9) |
| 21 | Unsafe path | `engine.lock` path a non-regular file other than a symlink (a symlink is reclaimed as corrupt, `lock.ts:156`), or another I/O error taking it (§2a); §4 step 2 `lstat` error other than `ENOENT`; step 3 non-socket; step 4 probe timeout, other probe error, socket changed before unlink, or `unlink` error other than `ENOENT`; step 5 `chmod`/mode/owner failure |
| 22 | Unexpected bind or listen error | The pre-`listen` path-length check fails (`socket path too long`, §4; Argus I4, review line 195; `logs/amend1/longpath.log`); `listen` fails other than `EADDRINUSE` (`EACCES` or anything else); or a fatal server `error` after listening (§3 c) |
| 23 | Shutdown deadline exceeded | A clean trigger (EOF, SIGINT, SIGTERM) whose shutdown did not finish within 5 s |
| 24 | Unexpected internal fault | An `uncaughtException` or `unhandledRejection` outside a shutdown already under way (§3 d); also how the launcher reads any code not in this table, except the two rows below |
| (signal) | Stopped by a signal `serve` did not handle | The launcher sees code `null` plus a signal name (Node v24.22.1, Bun 1.3.11) or code `143` with no signal (Bun 1.4.4, default SIGTERM) (`logs/amend1/rt/probes.log`). Read as **stopped**, reported with the signal, not 24. Bun 1.4.4's default-SIGTERM `143` cannot be told apart from row 143 (clean shutdown on SIGTERM); that is harmless, because the launcher reads both as stopped by SIGTERM |
| 1 (Windows, after the launcher's own kill) | Stopped by the launcher | `TerminateProcess(handle, 1)` (§4 Windows). Read as **stopped**, not 24, only when the launcher itself issued the kill |

**Precedence (every combination):**

| Situation | Exit |
| --- | --- |
| Startup check fails, in the order args → home → `engine.lock` → §4 steps 1-4 (re-verify before unlink) → listen → re-verify → step 5 (the listen step starts with the path-length check) | The **first** failing check's code (2, 20, 21 or 22) |
| Unexpected fault during startup, not one of those checks | 24 |
| EOF or signal during startup, before any check has failed | Startup is aborted, anything bound is closed and unlinked (§3 step 5 rule), locks released; 0 / 130 / 143 |
| Running; first trigger EOF / SIGINT / SIGTERM; shutdown finishes within 5 s (with or without a failing shutdown step) | 0 / 130 / 143 |
| Running; first trigger EOF / SIGINT / SIGTERM; deadline passes | 23 |
| Running; first trigger a fatal listener error | 22, whether or not the deadline passes |
| Running; first trigger an unexpected fault | 24, whether or not the deadline passes |
| Fault, listener error or step failure **during** a shutdown already under way | Treated as a failing shutdown step: the trigger's code, or 23 if a clean trigger's deadline passes |
| Second EOF or signal during shutdown | No change |
| SIGKILL | No code from `serve` (killed by signal 9; the launcher reads it as stopped). For an initialized `serve` this means it overran its 6 s exit bound (§3), since the launcher waits 7 s (§5); a never-initialized child is killed 2 s after SIGTERM (§5). Its locks are reclaimed at the next start unless the §2a crash-residue risk applies |
| Any other unhandled signal, or Windows `TerminateProcess` by the launcher | Stopped (signal row, or Windows exit 1 row); never 24 |

**stderr.** Every non-zero exit writes **one final reason line**, with a write callback before the exit (§3, "Explicit exit on every path"), `madc-engine serve: <reason>: <path>`, naming the reason and the socket or lock path (or `$MADC_HOME` for code 2), in the `auth-set` prefix style (`auth-set.ts:108`). Earlier stderr lines are logs. No secrets, no lock token, no environment dump, no stack trace. Code 2 for a bad `MADC_HOME` does not echo the rejected value beyond what `resolveMadcHome` already prints (`home.ts:26`).

## 7. Malformed input on the socket

Unchanged from stdio: a line that is not JSON gets `-32700`, valid JSON that is not a request gets `-32600`, both with `id: null` (M1 pin §4, lines 134 and 140-141; `wire.ts:22-40` and `server.ts:672-678` @ `bd037b4`), and the connection carries on. Each socket has its own `EngineConnection` (`socket.ts:83-98` @ `6e20176`), so one bad client, one client socket error (for example `ECONNRESET`) or one client disconnect ends only that connection; the listener and the other connections keep running. The stdio path has no line-length cap and this amendment adds none.

## 9. Out of scope

- §3 `room/updated` keeps its notification shape and its four reasons. §10 changes **when** two of its events fire (rulings 1 and 4, base line 40) and pins which thread each names; §10 ruling 7 changes base §2's unknown-key handling for `session/search` and `session/read`. These are base-pin changes, listed in §8 Replaced, and merging this amendment is the Founder changing base §2 and §3 (adopted with #71, D-625). Argus H1 on #73 remains a build gap, not a pin change.
- **`engine.lock` race residues (carried; accepting them is a Founder call).** Inside the M0 Amendment 2 §6 three-engine reclaim race: (1) two `serve`s can both lose the re-verify or meet each other's probe and **both exit 20, leaving no listener**; each launcher's re-probe then fails and the user retries; (2) there is a gap between §4's re-`lstat` (`dev`+`ino`) and the `unlink`, two path operations (COPILOT-PATTERNS #4). Neither can produce a second **reachable** listener: any later `serve`'s probe finds the live one (exit 20), and the shutdown unlink is `dev`+`ino`-checked. An atomic scheme (for example an `flock`-held lock or a rename-into-place bind) is **not adopted** here.
- §4 is unchanged. It still cites no Iris design spec (the evidence-bound rule is D-626; the Iris citation gap is D-618). Out of scope here.
- **Windows owner-only pipe ACL: an M3 gap, carried and unverified.** The pipe gets no owner-only ACL today (Argus I1, review line 192), and this amendment does not pin an API for one. It must be pinned before Windows is claimed as supported.
- **Bun 1.3.11 takes over a live socket path (carried risk, Argus P5 on #73's `5ea215b` pre-check).** On Bun 1.3.11 a second `listen()` on the path of a live listener **succeeds** and replaces it (new inode); Node 22.19.0 and Bun 1.4.2 return `EADDRINUSE` (Argus probe `logs/pr73-5ea/argus-dbl.mjs`, result "1.3.11: second listen SUCCEEDED; inode changed: true", `pr73-review-6e20176.md` line 377; re-run 2026-11-24, `logs/amend1/dbl-rerun.log`: Bun 1.3.11 same result, Node v24.22.1 and Bun 1.4.4 `EADDRINUSE`). The probe runs both listeners **in one process**; a two-process takeover was not measured. So on Bun 1.3.11 the §6 `EADDRINUSE` → 20 path cannot happen, and `engine.lock` (§2a) is the **only** thing stopping one `serve` from hijacking another's socket; a non-`serve` listener that binds between §4's probe and `listen` is replaced, not refused. No new runtime requirement is added; the `EADDRINUSE` mapping stays as a backstop for the runtimes that report it.
- **Bun's exit behavior, as measured** (`logs/amend1/rt/probes.log`, Bun 1.3.11 and 1.4.4): an uncaught exception or unhandled rejection without a handler exits 1; with `serve`'s handlers it exits the handler's code; a rejected top-level `await` reaches `uncaughtException`; an unsettled top-level `await` never exits (hangs until killed); a default SIGTERM ends 1.3.11 with code `null` and signal `SIGTERM` and 1.4.4 with code `143`. Bun has no published reserved-exit-code list that this amendment found, so whether Bun reserves any of 20-24 is still carried.
- **`engine.lock` crash residue: carried risk.** A reused or unsignalable (`EPERM`) pid keeps a crashed `serve`'s lock looking held (§2a). The pinned way out is the reason line plus the launcher's manual fix; a boot-time rule is not adopted and needs a Founder ruling.
- **Doctor does not see `engine.lock` residue.** `madc doctor`'s lock check lists `sessions/` only (`packages/cli/src/doctor.ts:748-751` @ `bd037b4`), so an orphaned `engine.lock.reclaim-*` or `engine.lock.tmp-*` in `$MADC_HOME` (M0 Amendment 2 §6 residuals), or a stale `engine.lock` itself, is not reported. Carried alongside the crash-residue risk above; a CLI-pin change, not made here.
- Who reconnects after a reused listener's launcher exits, and the desktop's reconnect UX, are M3-A2 build questions; this pin requires only that the launcher does not auto-retry or respawn (§5).
- Whether `serve` is built in PR #73 (M3-A1) or as the first step of M3-A2 is the Founder's call; this pin does not decide it.

## 10. Builder readings on PR #73, ruled (Hephaestus, local `5ea215b`, 2026-11-24)

Hephaestus built `room/updated` and the new methods to readings the base pin does not state. Each is ruled here against the base pin at `bd037b4` and `PIN-madc-M2-handoff-procedure.md` at `bd037b4`. No ruling adds or removes a method, param, result shape or error code, and `protocolVersion` stays `madc-m1/1`; rulings 1, 4 and 7 do change base pin behaviour (§8 Replaced), which merging this amendment ratifies.

1. **When `handoff` fires (accepted).** A handoff is reported once `handoff.out` has been appended (handoff pin step 2, line 89): exactly one `room/updated` `handoff` is emitted when the request finishes, whatever the outcome (`handoff.link`, `handoff.aborted`, or a failure that appends nothing further, handoff pin lines 106-114). A refusal before `handoff.out` is appended changed no file and emits nothing.
2. **`threadId` on `handoff` (changed from the built reading).** `threadId` is always the **source** thread, for a link and an abort alike, because `handoff.out`, `handoff.link` and `handoff.aborted` are all appended to the source file (handoff pin lines 13, 89, 103, 106). One field has one meaning; a client finds the target from the source's records via `session/read` or `room/inspect`. The built reading (target on a link, source on an abort) is not adopted.
3. **`thread` on connection shutdown (accepted).** When a connection shuts down, one `thread` event is emitted for each thread it had loaded, whether or not `session.close` was written (a failed close still unloads the thread). It goes to every other subscribed connection; the closing connection never receives its own. **At `serve` shutdown** (§3 step 2, where every connection closes), these `thread` events go only to subscribers whose sockets are still open and not yet ending: a connection that has already called `end()`, or is being destroyed, receives none.
4. **No double announcement (accepted).** A handoff target created on disk is announced only by the source's `handoff` event, and a cold thread loaded by `decision/resolve` only by its `decision` event. Neither also emits `thread`. One action, one event.
5. **Stale `ENOENT` (already pinned).** Covered by §4 step 4 of this amendment: `ENOENT` on a path step 1 verified as a socket is stale.
6. **Typed startup refusals to exit codes (already pinned; mapping stated).** Under §6: `live` → 20; `symlink`, `not-socket`, `probe-timeout`, `probe-failed`, `replaced` (socket changed before unlink), `stat-failed` (an `lstat` or `unlink` error other than `ENOENT`) and `chmod-failed` → 21; `listen-failed` → 22, except `EADDRINUSE` → 20 (a backstop that may never fire on Bun 1.3.11, where a second `listen()` takes over a live path instead of failing; §9). A socket path too long for `sun_path` is refused **before** `listen` by the path-length check (§4), reason `socket path too long` → 22, on every runtime (Bun would otherwise listen on it, `logs/amend1/longpath.log`). Lock outcomes (§2a): lock **held**, attempts **exhausted**, or token **lost** at a re-verify → 20; a lock **path** error (non-regular file other than a symlink) or lock **I/O** error → 21. Lifecycle and signals are §3 and §5. The Windows pipe ACL stays carried (§9). Whether `serve` is built in PR #73 or in M3-A2 is still the Founder's call (§9).
7. **Unknown keys on `session/search` and `session/read` (refused).** Both refuse any key outside their params (base lines 26 and 34) with `-32602 InvalidParams`, matching `room/inspect` (base line 22) in the same pin, and the key is not echoed, as the decision-inbox pin already does for its closed key sets ("never echoing the caller key", `PIN-madc-M2-founder-decision-inbox.md` lines 9 and 20 @ `bd037b4`). The base lines are silent and `6e20176` accepts unknown keys on both (`server.ts:871-881`, `:883-889` @ `6e20176`); this closes them. **A deliberate choice for the new methods,** not a repo-wide rule: `main` today mixes three behaviours (`server.ts` @ `bd037b4`): `thread/start` and `turn/start` ignore unknown keys (`:1231-1240`, `:2000-2007`); `seat/list` and `provider/list` refuse and echo the key names (`:1126-1128`, `:1142-1144`); `decision/list` refuses without echoing (`:833-834`).
